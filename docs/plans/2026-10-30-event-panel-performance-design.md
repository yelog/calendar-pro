# 日程详情与编辑器卡顿：分析与优化设计

日期：2026-10-30。状态：已完成代码分析、隔离复现、实施方案及阶段 A/B 自动化回归；真实应用交互和 Instruments 性能采样尚未执行。

实施方案：[2026-10-30-event-panel-performance.md](2026-10-30-event-panel-performance.md)

## 结论

当前代码存在可复现的窗口尺寸反馈循环：SwiftUI 测量高度后异步回写 `NSPanel`，窗口变化又产生下一批测量。同时 `NSHostingController` 的自动尺寸约束参与窗口调整，旧测量值不断反向影响新布局。循环持续占用主线程，因此切换日程、关闭弹层、进入编辑及日期选择都可能排队。

这不是仅凭源码推测：使用仓库原始视图、合成的内存 `EKEvent` 和隐藏 `NSPanel`，复现了每秒数百次调窗。带少量备注的详情页还会在一次运行中调窗超过一千次。候选方案改为测量内容自然高度、限制滚动视口、由控制器独立管理窗口尺寸后，相同场景只需 0～1 次手动调窗并保持稳定。

不能将用户实际全天事件的全部延迟直接归因于该循环：没有捕获到真实卡顿时的主线程栈，也没有读取用户事件内容。已确认的是当前实现确实具有能够造成该类卡顿的缺陷；数据读取与备注排版仍是需要同时控制的额外成本。

## 证据与复现范围

分析基线：`7309991 feat(events): support cross-day event editing`。开始分析时工作区干净。该提交新增编辑器高度回写，并调整了详情页的全天结束日辅助方法；详情页三路高度测量、备注富文本排版在此前已存在。

环境为 Apple Silicon、macOS 27.0.1、Apple Swift 6.4；探针使用 `-Onone`。探针直接编译以下生产实现：日期草稿、详情/编辑视图、日程请求和模型、会议链接解析、文字与面板尺寸辅助；仅替换本地化和两个非关键的徽章/平台图标。事件未保存到 EventKit，面板未显示到用户桌面，也未调用真实编辑保存路径。

探针的隐藏宿主复现 `presentPanel` 的关键步骤：设置内容控制器、读取 fitting size、设置窗口尺寸，然后运行主线程 RunLoop；高度回报沿现有尺寸规则回写。它没有构建完整菜单栏应用，也没有模拟点击或测量真实鼠标响应延迟。

- 仅将 `setContentSize` + `setFrame` 减为一次设置，循环仍存在。

## 调用链与根因

### 编辑器反馈循环

关键位置：

- `CalendarPro/Views/Popover/CalendarItemComposerView.swift:96`：中间 `ScrollView` 使用 `maxHeight`，根视图可受窗口高度影响。
- 同文件 `:111`：在根视图背景中测量整体当前高度。
- 同文件 `:712`、`:731`：测量回调与转发各使用一次 `DispatchQueue.main.async`。
- `CalendarPro/App/EventDetailWindowController.swift:205`：安装 `NSHostingController` 后同步触发布局并设置窗口尺寸。
- 同文件 `:230`：高度回调继续执行 `setContentSize` 和 `setFrame`。

当前回报的是已经受窗口约束的布局结果。第一次 fitting、窗口显示和随后高度变化产生不同测量；异步队列按顺序继续消费旧高度，旧尺寸又产生下一批测量。`> 1pt` 判断只能挡住相近数值，挡不住 360 / 419pt 这种来回交替。

hosting 自动约束与手动调窗同时存在，会让同一窗口有两个尺寸决策来源。修复必须同时处理尺寸所有权和测量语义。

### 详情页反馈循环

关键位置：

- `CalendarPro/Views/Popover/EventDetailWindowView.swift:87`：测总高度。
- 同文件 `:287`：测滚动视口高度。
- 同文件 `:339`：测滚动内容高度。
- 同文件 `:436`：计算 `containerHeight - detailViewportHeight + detailContentHeight`。
- 同文件 `:495`：三个回报分别异步入队，状态未作为一次完整测量提交。

三份状态可能来自不同布局轮次。例如总高度已经更新，视口高度仍是旧值，暂时合成了一个不存在的自然高度，再被立即写回窗口。短备注、展开/折叠及视口适配会改变布局轮次；这解释了为何无备注样本可稳定，部分备注样本循环，而很长备注可能因上限钳制暂时稳定。

### 为什么多个操作同时慢

`EventDetailWindowController` 标记为 `@MainActor`。`PopoverInteractionMonitor.start` 的全局鼠标和失焦回调也调度到 `MainActor`，最终调用 `closePopover` / `popoverShouldClose` / `closeEventDetailWindow`。这些路径没有数秒延迟定时器；当布局与回调持续占用主线程时，关闭请求和其他交互只能等待。

`handleEventSelection` 本身只切换选中状态并展示详情，没有重新拉取日程数据库。不能因为关闭慢就先增加外部点击监听，或把关闭行为搬到后台线程；AppKit 窗口操作仍必须留在主线程。

### 全天日期算法不是当前第一瓶颈

`CalendarEventScheduleDraft.displayedEndDate` 只执行日边界和前一日计算；`coveredDayCount` 按日历日计算，不遍历事件跨度。

在固定 Gregorian / Asia/Shanghai 的微基准中，这两项合计执行 10,000 次约 48.1ms，单次组合约 4.8μs。因此不应为这次卡顿回退多日全天语义，也不应将按日历日运算替换成每一天 86,400 秒。夏令时和跨天保存契约必须保留。

相同机器微基准：42 个日期 × 10 次重算，分别为每格新建 formatter 83.6ms、复用一个 formatter 1.05ms、值类型 `Date.FormatStyle` 0.82ms。日期弹层这一轮约 8ms 的初始化成本本身不足以解释数秒等待，但在布局循环中会被放大。上述比率是孤立格式化基准，不是整个界面加速比。

112KB 合成备注扫描 20 次，会议链接约 322ms、DataDetector 约 654ms。实际费用随文本变化；不代表用户备注具有相同大小。消除重复扫描应优先于引入后台富文本系统。

## 推荐方案

### P0：拆开自然内容高度、滚动视口高度和窗口高度

编辑器分别测量标题区、完整表单内容和底部按钮；详情页分别测量标题、摘要、可选会议操作、完整详情内容和底部按钮。

测量对象必须是在固定宽度下可独立确定的内容。滚动内容采用垂直自然尺寸，根容器和滚动视口不参与自然高度来源。以完整测量快照进行计算，不用“总布局高度减旧视口高度”反推。

计算规则：

```swift
let chromeHeight = headerHeight + summaryHeight + meetingHeight + footerHeight
    + outerPadding * 2 + sectionSpacing * sectionGapCount
let naturalHeight = chromeHeight + contentHeight
let viewportHeight = min(contentHeight, max(0, maximumHeight - chromeHeight))
```

编辑器没有摘要/会议区，将对应项排除，间距按实际参与布局的区域数计算。标题/底部高度需测量，不再减固定 `125`。视口设置明确的 `height`；自然高度独立报告给控制器。

控制器根据屏幕上限钳制自然高度，保留现有顶部对齐、理想高度和滚动行为；详情与编辑器使用同一个有效高度上限。

### P0：一个窗口只有一个尺寸管理机制

日程详情和新建/编辑宿主由控制器手动管理窗口尺寸，关闭这些宿主的自动尺寸约束。首次显示使用现有理想高度或有界的 `sizeThatFits(in:)`，随后由内容测量收敛；关闭自动约束后不能继续假定 `view.fittingSize` 一定有效，探针中它返回 `(0, 0)`。

同一轮只消费最新测量，保留 `> 1pt` 与有限正值校验；不要为每一个测量创建额外调窗任务。每次展示绑定 generation 和具体 panel，切换日程、详情转编辑和关闭时使旧任务失效，避免旧页面高度作用于新页面。

这些变化针对手动调窗的日程详情/编辑宿主。提醒事项详情没有现有动态高度回调；如共享 `presentPanel` 修改影响到它，需要显式保留其策略并回归验证，不能直接全局禁用 sizing 后仍用失效的 fitting size。

### P1：减少每次视图更新的工作

- 日期控件采用捕获同一 calendar / locale / time zone 的 `Date.FormatStyle` 或面板作用域 formatter。可访问性日期标签也复用格式，语言/时区变化要正确失效，避免永久静态 formatter 锁住首次语言。
- 备注富文本只在 notes 改变时更新 `textStorage`；宽度变更只重新测量，颜色使用系统动态颜色。复用 detector；保留链接点击与文字选择。
- 将文本高度测量集中到一个途径，避免 `sizeThatFits` 与异步 state 回写同时决定高度；不在更新和测量时反复替换相同文字。
- 预编译会议匹配规则；将同次详情展示的静态元信息在适当的更新边界复用。参与状态更新和外部数据变化必须能使快照失效，不以永久缓存换取错误显示。

### P2：在有证据时调整 EventKit 数据路径

先删除重复日历枚举，使用已加载日历立即打开编辑器。授权变化和 store change 时集中刷新目录，必要时显示轻量加载态。

若 Instruments 仍显示 EventKit 同步查询占用主线程，再将读取隔离到串行 worker / actor，`EKEventStore` 的创建和使用保持在同一隔离域，对界面返回值类型快照。写入使用标识在 store 所属隔离域重新解析目标，保持现有 `.thisEvent` 和未修改字段。不把捕获现有 `EKEvent` / `EKEventStore` 的 `Task.detached` 当作完整线程方案，也不通过 `@unchecked Sendable` 绕过检查。

这属于后续可选的数据路径调整，不能在修复调窗循环时顺便重构整个 EventKit 层。当前最小完整修复是 P0 + 与重绘直接相关的 P1。

## 验收

1. 无交互时窗口高度在少量初始化轮次内收敛；稳定 3 秒，最后 2 秒无主动调窗。
2. 连续切换日程、关闭/重开、详情转编辑时，旧测量不得改变新页面。至少覆盖一个会使备注区出现/消失的组合。
3. 全天、定时、跨天、短/6 行/200 行备注、可选会议操作、非法日期提示均稳定。
4. 正常屏幕和约 360pt 可用高度下，标题及取消/保存可达，超出内容能滚动；验证备注展开折叠、输入错误和语言切换。
5. 在运行应用内记录切换日程、失焦关闭、编辑打开、日期弹层打开的延迟；目标为预热后 p95 < 100ms，不出现 > 250ms 主线程单次阻塞。该目标尚未实际测得。
6. 原全天半开区间、覆盖末日、跨夏令时、未改日期精确保留及提醒事项共用控件测试全部通过。
